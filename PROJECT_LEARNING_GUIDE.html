01

先把项目跑起来

学习任何测试框架的第一步都是建立“输入、执行、输出”的直觉。本项目的输入是 Python/YAML 测试，用 pytest 执行，输出终端结果、HTML、JUnit 和 Allure 数据。

最小运行路径

  1. 确认 mall 网关和后端依赖已启动。
  2. 安装 requirements.txt。
  3. 先执行 smoke，再执行全量。
  4. 打开根目录下的 reports/report.html。

环境依赖

  • 网关：localhost:8201
  • 业务服务：auth / portal / search / admin
  • 中间件：Nacos、Redis、RabbitMQ、MySQL
  • ES 用例额外依赖 Elasticsearch 和 pms 索引

常用命令

# 安装依赖
python -m pip install -r requirements.txt

# 11 条核心冒烟用例
python -m pytest -m smoke

# 131 条业务用例，默认生成 reports/report.html
python -m pytest tests

# 指定模块
python -m pytest -m "login or cart"

# 双进程执行
python -m pytest tests -n 2

# 只收集、不执行，用于检查用例规模
python -m pytest tests --collect-only -q -o addopts=""
为什么推荐 python -m pytest？它明确使用当前 Python 解释器里的 pytest，能减少电脑上多个 Python/虚拟环境造成的“装了依赖却导入失败”。

怎么看结果

状态含义下一步
passed测试逻辑执行且所有断言成立检查是否符合预期覆盖，不代表接口绝对无缺陷
failed测试主体断言失败查看响应、断言行与 Allure 附件
errorfixture 准备/清理或框架执行异常优先看 setup/teardown 堆栈
skipped条件不满足而主动跳过本项目常见原因是数据库校验未启用

目录结构：先知道去哪里找

pytest-framework/
├─ config/           全局配置与 Pydantic 模型
├─ data/             Python 参数化数据
├─ fixtures/         业务前置、复用和清理
├─ tests/            真实 API 测试
├─ engine/           YAML 场景执行器
├─ cases/            真实 API YAML 场景
├─ utils/            HTTP、断言、DB、报告工具
├─ framework_tests/  框架离线自测
├─ mock_server/      仅供框架自测的 Flask 服务
├─ scripts/          CLI、Linux CI、钉钉通知
├─ pytest.ini        pytest 默认配置与 marker
├─ conftest.py       全局 fixture 插件注册
├─ Jenkinsfile       Jenkins Linux 流水线
└─ requirements.txt  Python 依赖

阅读顺序

  1. pytest.ini：入口规则。
  2. conftest.py：fixture 从哪里注册。
  3. tests/test_login.py：最容易理解的业务测试。
  4. fixtures/session_fixtures.py：配置与登录客户端。
  5. utils/http_client.py：请求究竟怎样发出去。
  6. utils/assertions.py：成功与失败如何判定。
  7. 再进入购物车、订单和 YAML 引擎。
判断代码放哪里：接口输入组合放 data/，可复用前置放 fixtures/，业务断言放 tests/，跨业务通用能力放 utils/ 或 engine/。

为什么不是 POM

POM（Page Object Model）用于 UI 自动化，把页面元素和页面操作封装成对象。本项目没有浏览器页面元素，使用的是“业务域 fixture 分层 + HTTP 客户端 + 场景引擎”。面试时写 POM 会暴露概念混淆。

03

一次测试请求到底经历了什么

点击下面任一步骤，查看它在项目中的职责。先掌握这条链路，再看具体文件就不会迷路。

用登录成功测试举例

def test_member_login_success(settings, anon_client):
    response = anon_client.post(
        settings.portal("/sso/login"),
        params={"username": "test", "password": "123456"},
    )
    payload = assert_success(response)
    assert payload["data"]["token"]
  1. pytest 发现函数名以 test_ 开头。
  2. 看到参数 settings、anon_client，从注册的 fixture 中寻找同名对象。
  3. settings.portal 生成 /mall-portal/sso/login。
  4. ApiClient 将其拼到 http://localhost:8201 后发送。
  5. assert_success 同时检查 HTTP、JSON 结构和业务 code。
  6. 请求/响应进入 Allure；Session 在测试会话结束时关闭。
04

你必须掌握的 pytest 核心概念

pytest 默认发现 test_*.py / *_test.py 文件、Test* 类和 test_* 函数。本项目用 pytest.ini 将默认测试目录设为 tests。

一个测试函数配多组输入，收集时展开成多个 node。本项目有 29 处参数化定义，这就是 66 个函数能够展开为 131 条业务用例的重要原因。

@pytest.mark.parametrize("quantity", [1, 2, 5])
def test_cart_update_quantity(quantity):
    ...

Marker 是用例标签。模块标签表示业务归属，场景标签表示测试维度。它们可以重叠，例如一条订单主链路既是 order 又是 flow。

pytest -m smoke
pytest -m "order and flow"
pytest -m "validation and not es"

fixture 是 pytest 的依赖注入机制。测试函数参数名就是依赖名，pytest 自动创建依赖、缓存 scope 对应的对象，并按相反顺序执行 teardown。

Scope 怎么选

Scope生命周期项目中的例子选择原则
session整个测试会话一次settings、member_client创建昂贵且可安全共享
module一个测试模块一次es_available同模块共享环境检查
function每条用例一次cart_item_id、generated_order有状态、需要独立创建和清理
常见误区：fixture 不是普通 helper。普通 helper 由你主动调用；fixture 由 pytest 根据依赖图调度，负责 scope、缓存和 teardown。
05

Fixture：项目最值得讲的设计

真实 API 测试最大的难点不是发请求，而是“前置数据从哪里来”和“执行后如何不污染环境”。本项目用 30 个 fixture 描述依赖图。

settings→ member_client→ worker_product→ cart_item_id→ confirm_order→ generated_order→ paid_order_id

yield fixture 为什么重要

@pytest.fixture
def cart_item_id(settings, member_client, product_id, sku_id):
    # setup：创建自己的购物车条目
    item_id = create_and_find_item(...)

    yield item_id

    # teardown：无论测试通过还是失败，都尝试清理
    delete_cart_item(settings, member_client, item_id)

yield 前是 setup，返回给测试的是 yield 后面的值；测试结束后，pytest 回到 yield 下一行执行 teardown。依赖越晚创建，越早清理。

本项目的数据隔离策略

购物车

写入前确认同款商品不存在；只按自己创建的 item id 删除，避免清空共享账号已有数据。

并行 worker

根据 gw0/gw1 分配不同商品和 SKU，避免同款商品被后端自动合并造成串扰。

订单

未支付订单执行取消再删除；已支付订单因后端状态规则无法删除，只记录并保留。

面试亮点：不要只说“用了 fixture”。要说你如何利用 fixture 的依赖图和 teardown 解决真实数据副作用，并说明为什么已支付订单不能承诺 100% 清理。

一条好用例应该包含什么

  1. 明确测试意图：名称和 docstring 说明验证什么，不只是接口名。
  2. 受控前置：通过 fixture 准备 token、商品、购物车或订单。
  3. 单一核心行为：本条测试关注一个主要风险。
  4. 业务断言：不仅看 HTTP 200，还看 body code、结构、状态和数据变化。
  5. 后置验证：更新后重新查询，确认服务端状态确实发生变化。
  6. 清理策略：能删则删，不能删则明确记录边界。

测试维度

正常与主链路

smoke=11，flow=10。验证核心功能和跨接口状态流转。

异常与权限

validation=31，permission=11。覆盖缺参、错类型、非法 token。

07

YAML 场景引擎：把流程从 Python 代码中抽出来

简单接口用 Python 测试最清楚；多接口流程会反复出现“发请求、提取字段、传给下一步”。场景引擎把这些重复动作抽象成 YAML。

cases:
  - name: 会员登录成功
    steps:
      - name: 登录并提取 token
        request:
          method: POST
          path: /mall-portal/sso/login
          params:
            username: ${member_username}
            password: ${member_password}
        extract:
          token: $.data.token
        assertions:
          - actual: $.code
            comparator: eq
            expected: 200

对应执行过程

  1. load_yaml 使用 safe_load 读取文件。
  2. CaseFile.model_validate 用 Pydantic 校验结构。
  3. render 将变量替换到请求中。
  4. ScenarioRunner 发送请求。
  5. find_one 用 JSONPath 提取 token。
  6. Runner 自动把 token 设置到客户端。
  7. AssertionEngine 执行断言。

变量与动态值

写法作用类型
${order_id}读取场景上下文变量整字段替换时保留原类型
order-${order_id}在字符串中插值字符串
${ENV:NAME}读取系统环境变量字符串
${{uuid}}生成无连字符 UUID字符串
${{timestamp}}当前秒级时间戳整数
${{random_int:1,100}}生成闭区间随机整数整数
什么时候不要用 YAML？

复杂循环、条件分支、特殊清理或大量自定义 Python 计算用 YAML 会变得难读。此时直接写 Python 测试更合适。数据驱动不是“所有测试都 YAML 化”，而是选择表达成本最低的形式。

08

HTTP 客户端、重试与断言

ApiClient 做什么

  • 复用 requests.Session 连接池。
  • 统一 base URL、Accept 和 Authorization。
  • 默认 15 秒超时，可由环境变量覆盖。
  • 记录方法、URL、状态码和耗时。
  • 把请求和响应附加到 Allure。

ApiClient 不做什么

  • 不把所有 4xx/5xx 自动判为异常。
  • 不替业务测试决定 code 是否正确。
  • 不盲目重试 POST 下单和支付。
  • 不把连接失败静默吞掉。

为什么只重试幂等请求

GET 读取超时后再读一次，通常不会产生额外业务数据；POST 可能已经在服务端成功，只是响应途中断开。如果客户端自动重试，可能重复下单、重复扣款。因此项目只对 GET、HEAD、OPTIONS 的连接错误和超时重试。

面试陷阱：“失败重试”不等于“所有失败都再跑一次”。HTTP 业务错误重试通常无意义，非幂等写请求重试还可能扩大事故。

三层断言思路

传输层

HTTP 状态码、响应是否为 JSON、Header。

协议层

CommonResult 是否有 code/message/data，分页结构是否完整。

业务层

订单状态、数量变化、列表包含关系、非法请求没有产生数据。

场景引擎支持的比较器

eq、rv、ne、contains、not_contains、in、not_in、gt、ge、lt、le、exists、not_exists、regex、length_eq、type，以及数据库比较 db/db_eq。

09

数据库双重校验与测试报告

为什么接口通过还要查数据库

接口返回成功只说明服务“声称成功”。关键链路还需要确认数据库最终状态。例如会员信息接口返回的 username 是否与 ums_member 对应记录一致。

SQLAlchemy 设计

  • mysql+pymysql 驱动。
  • pool_pre_ping=True 检查失效连接。
  • pool_recycle=1800 回收长连接。
  • URL.create 避免密码出现在字符串 URL。
  • 只允许 SELECT/SHOW/DESCRIBE/EXPLAIN。
  • Session 结束统一 dispose Engine。
$env:PYTEST_DB_ENABLED = "true"
$env:PYTEST_DB_HOST = "127.0.0.1"
$env:PYTEST_DB_USER = "root"
$env:PYTEST_DB_PASSWORD = "你的密码"
$env:PYTEST_DB_NAME = "mall"

python -m pytest tests/test_yaml_scenarios.py -m database
当前证据边界：数据库适配层单测覆盖率 95%，但本机真实 DB 用例因未提供 root 密码而跳过/无法认证。简历可以说“实现能力”，不能说“数据库校验已在 CI 全量稳定运行”。

三种报告各自解决什么问题

报告适用场景特点
pytest-html本地快速查看、发送单文件无需服务，直接打开 reports/report.html
Allure失败诊断和 CI 展示步骤、请求/响应附件、环境信息
JUnit XMLJenkins/GitHub Actions 机器读取用例状态、耗时、趋势的标准输入

Allure 工具会对 10 类敏感字段脱敏：Authorization、password、passwd、token、tokenHead、access token、refresh token、authCode、phoneNumber、telephone。响应附件超过 4000 字符会截断，避免报告膨胀。

CI/CD、Linux 与 xdist

Jenkinsfile

  1. Linux agent checkout 并清理旧工作区。
  2. 创建 venv，安装 requirements。
  3. 始终执行 11 条框架自测。
  4. 按 RUN_E2E 决定是否执行真实 API。
  5. 支持 marker 和 worker 数参数。
  6. 发布 JUnit、Allure、HTML，按需钉钉通知。

GitHub Actions

  1. push/PR 自动执行离线框架自测。
  2. workflow_dispatch 手动触发真实 E2E。
  3. 账号和地址从 Secrets 注入。
  4. 归档报告 artifact。

为什么并行只快了 1.4%

模式CollectedPassedSkipped耗时
串行13113018.818s
xdist -n 213113018.695s

本地 API 延迟低，套件规模小，创建 worker、重建 session fixture 和进程调度产生固定成本，所以收益有限。并行能力的价值主要体现在更大用例集或远程高延迟环境；不能脱离测量宣称“2 小时降到 15 分钟”。

并行不是加一个 -n auto 就结束。必须确认共享账号、购物车合并、订单状态、随机数据和 teardown 都能在 worker 间隔离。

失败时如何系统排查

排错不要从“是不是代码有 bug”开始猜，而要先判断失败发生在哪一层。

现象优先检查典型原因
ConnectionError / Timeout网关探测、服务注册、中间件服务未启动、端口错误、Nacos 未注册
HTTP 200 但断言失败body code、message、data网关/业务层把错误包装在 JSON 中
401/403 异常是否走网关、tokenHead、Authorization直连服务绕过鉴权或 Token 过期
setup errorfixture 堆栈、前置接口响应账号登录失败、无商品、无地址
teardown erroryield 后清理代码解析错资源 ID、资源状态不允许删除
只在 -n 2 失败worker 是否共享商品/购物车/订单并发串扰或清理了另一个 worker 的数据
ES 用例跳过mall-search、9200、pms 索引ES 未启动或索引未导入
DB OperationalError 1045PYTEST_DB_USER/PASSWORDMySQL 凭据错误或未配置

推荐排错命令

# 保留实时日志，只跑一条
python -m pytest tests/test_login.py::TestMemberLogin::test_member_login_success -s -vv

# 首个失败后停止
python -m pytest tests -x

# 查看 fixture 解析
python -m pytest --fixtures

# 只收集，验证 marker/参数化
python -m pytest tests --collect-only -q -o addopts=""

# 生成独立失败报告
python -m pytest -m order --html=reports/order-debug.html --self-contained-html
本次强化时真实遇到的 teardown 问题

原 confirm_order fixture 在 yield 后把确认单响应误当成正式订单响应，访问 data["order"]["id"]，导致 5 个用例主体通过但 teardown 报 KeyError。修复方式是让确认单 fixture 直接 return，把订单清理移动到真正创建订单的 generated_order fixture。这个案例很好地说明了 failed 与 error 的区别。

12

面试怎么讲：从“用了什么”升级到“为什么这样设计”

60 秒项目介绍

这是一个面向 mall-swarm 电商微服务的接口自动化测试框架。我用 Python、pytest 和 requests 统一通过网关访问真实 API，覆盖登录、商品、搜索、购物车和订单五个业务域，共 131 条业务用例、32 个路由。框架用业务域 fixture 管理前置和清理，用 YAML/Pydantic/JSONPath 编排跨接口场景，并提供 SQLAlchemy 数据库双重校验、HTML/Allure/JUnit 报告和 Jenkins/GitHub Actions CI。项目重点解决了真实测试数据隔离、非幂等请求重试风险和 xdist worker 串扰问题。

高频追问与回答框架

1. 为什么要封装 ApiClient，直接 requests 不行吗？
回答：直接调用可以完成单条测试，但会重复 base URL、Token、超时、日志和报告逻辑。统一客户端让测试只关心业务输入与断言，同时把重试边界和敏感信息处理放在一个位置。需要强调客户端不做业务断言，避免职责混乱。
2. 为什么 POST 不重试？
回答：客户端超时不代表服务端没有成功。POST 下单可能已经落库，重试会重复创建。项目只对 GET/HEAD/OPTIONS 的连接异常重试，业务 4xx/5xx 不重试。
3. Fixture 和普通函数有什么区别？
回答：fixture 由 pytest 依赖注入和调度，支持 scope、缓存、依赖图和 yield teardown；普通函数由代码主动调用，不具备生命周期管理。
4. 如何保证并行执行不串数据？
回答：服务端会合并同商品同 SKU 的购物车条目，所以框架按 worker id 分配不同商品；购物车按 item id 精确删除；清空场景使用独立 Faker 会员；订单按状态选择清理策略。
5. YAML 数据驱动有什么优缺点？
回答：优点是流程和数据可读、跨步骤提取可复用，新增同类场景不用改执行器；缺点是复杂控制流和自定义清理表达困难，因此复杂用例保留 Python。
6. 为什么接口返回 200 还可能失败？
回答：本项目网关可能用 HTTP 200 包装 body code 401。必须同时校验 HTTP 层、CommonResult 协议层和业务数据层。
7. SQLAlchemy 在测试框架里解决什么？
回答：提供统一 Engine、连接池和断线检查，支持 API 与数据库最终状态比对；同时限制只读 SQL，避免测试断言误写业务库。
8. 你发现过什么真实问题？
回答：仓库沉淀了 12 项契约差异，例如非法购物车参数写入脏数据、商品非法 ID 触发 500、emoji 搜索触发异常、订单接口返回结构不一致。回答时挑 2 个讲“发现方式、风险、断言和清理”。
9. 为什么 xdist 提升不明显？
回答：本地低延迟且只有 131 条，worker 启动和 fixture 重建抵消收益。实测 8.818s 到 8.695s，只有约 1.4%，所以不能夸大并行效果。
10. 这个项目下一步怎么改进？
回答：补齐真实 DB 凭据和 Jenkins Linux 首跑，建立 Allure 历史与连续 20 次稳定性采样，为 12 项已知差异绑定缺陷编号，并逐步收紧服务修复后的兼容断言。

术语表与 7 天学习计划

术语表

API
系统之间约定好的调用入口、参数和响应。
Fixture
pytest 管理的测试依赖、生命周期和清理单元。
Marker
用例标签，用于选择模块或测试维度。
Parametrize
用多组数据展开同一个测试逻辑。
幂等
同一操作重复执行，业务最终效果与执行一次相同。
JSONPath
从嵌套 JSON 中定位和提取字段的表达式。
Teardown
测试执行后的资源释放和数据清理阶段。
xdist
pytest 多进程分发与并行执行插件。
Allure
支持步骤、附件和历史展示的测试报告体系。
JUnit XML
CI 系统读取测试状态和耗时的标准结果格式。
连接池
复用数据库或 HTTP 连接，减少重复建立连接成本。
契约差异
测试规则、接口文档与真实响应行为不一致。
